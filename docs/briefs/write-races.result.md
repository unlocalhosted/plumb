# Writes, hot reload and the network: the audit

The races in docs/briefs/stamping-everywhere.md, "Writes, hot reload and the network", against the write path as it was
at 53a52fc (the guarded writes in src/session/engine.ts, undo handles and traces, apply/apply-all, the overlay's request
layer in overlay/src/api.js). Each row: whether the code handled it before this layer, the e2e that reproduces it through
the real boundary, and the evidence. "Fixed here" names what this layer added, each with its failing test first.

| Race | Handled before? | Test | Evidence |
|---|---|---|---|
| Your editor saves while Plumber writes | yes: every write re-reads the file, compares `sourceHash` with the sent hash before and after, under the file's open descriptor (engine.ts `apply`, `rewrite`, `writeText`, `undoOne`: `if (sourceHash(...) !== hash) throw new UsageError(staleFile)`) | e2e/edits.test.mjs "finding 3: atomic-save / concurrent-save cannot return success for discarded edits"; e2e/write-stress.test.mjs "a concurrent writer racing Plumber's writes" | 40 writes per round against an editor saving whole files every 150 ms: 20–27 land, the rest are refused with "changed", the file parses after every write (3 rounds, run 3 times). A writer every 3–40 ms leaves no window at all: 40 of 40 refused, nothing lost, nothing torn |

## Still open after this layer

- Per-file serialization is the session's single queue: stronger than per file, and so a long write to one file delays a
  write to another. Not changed here; the spec asks for ordering, which this gives.
- A hidden page's missed Fast Refresh render (above) is not Plumber's to fix; what Plumber owes, never answering about
  old code, holds.
- Next says "built" just before its client applies the update, so the overlay's generation on Next advances a moment
  (80 ms settle) before React has re-rendered; a question asked in that moment is answered from the file on disk, and
  a stamp that still carries the old hash is refused, so nothing about the old code is shown. Next offers no public
  "update applied" signal (`__NEXT_HMR_CB` fires only in its own test mode).
- Two older tests leaned on the in-place write: e2e/edits.test.mjs "finding 3: concurrent-save" injected its editor save
  through the descriptor's `truncate`, which the rename no longer calls; it now saves when the checked descriptor closes,
  and the write is still refused. e2e/apply-all-hot.test.mjs "a save from an editor … is not held" waits 5 s for Vite's
  update and failed once under the full batch, passing alone and in the batch that followed: a timing window of the
  test, not a held update.
