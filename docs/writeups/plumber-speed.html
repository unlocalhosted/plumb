React Plumber · engine and server · 13 November 2026

Plumber was making the app it inspects slow. One day of measuring fixed most of it.

Plumber reads a running React app and judges its design against the project's own tokens. On a big page it took up to 52 seconds to read, sent 811 MB to draw one list, and dropped scrolling to 7 frames a second while open. This is how each of those was found and fixed, in the order it happened, with the number behind every claim.

Read of the big page, warm30–52 s 6–9 s
Sent to draw one page811 MB 12 MB
Scrolling with plumber open7 fps 53 fps
Moving the pointer, plumber open15 fps 59 fps

The two apps every number comes from

algorecallA large app with a 15,907-element list page and 2,411 source files. The worst case.
crafting-uiA small design-vocabulary app. The everyday case. Alone it scrolls at 57–60 frames a second.

Measured with headless Chromium driven by scripts, with real wheel and pointer input, usually one or two runs per state. Heavy runs on algorecall went to a separate server, because the laptop was swapping.

How the work was done

One rule held all day: time it before touching it. The first design guessed that some rules were expensive. The timer said no rule was heavy, and that the real cost was the same work being done again and again. Every step below starts with a measurement that surprised us.

01

The page was judged six times per read

Found by
A counter on every time the engine threw its findings away, with who asked.
Cause
Any fact that arrived late, such as the server's answer about which component an element is, was treated as "everything may have changed". All 82 rules then ran on all 15,907 elements again, once per batch of answers.
Fix
The engine notes which element asked for which late fact and re-judges only those. Page-wide rules keep their result while the page is unchanged.

02

811 MB sent to draw one page

Found by
One server answer taken apart field by field.
Cause
98% of the bytes were each finding's list of every edit it could lead to anywhere in the project, 434 on average. The overlay drew none of them. A second path, the trace of where an element's classes are written, carried the same baggage: 42 MB for 31 elements, one header link alone 22.5 MB.
Fix
Keep hot and cold apart. A page is sent what it draws; the edits are fetched on their own when a fix is applied, which the overlay already did.

The clock did not move with the second cut (16.7 and 17.0 s). Bytes were no longer where the time went, which pointed at the next step.

03

889 questions asked one at a time

Found by
The request timeline of one read: a wall of 889 separate requests, each waiting about 18 s.
Cause
One at a time at every level. The overlay asked per element. The server indexed the element's file again for each question. The page was reported and redrawn after every trickle of answers, 20 times.
Fix
Where there is one, there are many. Questions ride the batch other readings already use, the server keeps a file's index while its text is unchanged, and the engine is told once when nothing is still being asked.

04

Open, plumber dropped scrolling to 7 frames a second

Found by
The same page measured four ways (plumber blocked, loaded, reading, open), then a CPU profile of four seconds of scrolling. Over 90% of the time was one browser call, elementsFromPoint, asking "what covers this element?" thousands of times a frame.
Cause
Every frame re-measured everything, whatever caused the frame. A pointer move changes what is lit, not where things are, and still re-measured the page.
Fix
Ask less. Measure only when the page may have moved; mid-scroll, measure only what is lit; confirm what is covered in 6 ms slices after drawing. A cheaper probe that looked 17 times faster was rejected once its answers were checked: it was hitting plumber's own layer.

05

The page froze while plumber read it

Found by
A profile of one read with its long tasks listed. Each freeze was one whole-page judgement in a single block.
Cause
The engine's smallest unit of work was the whole page.
Fix
The smallest unit is now 8 ms. Kept findings answer at once; the rest is judged a slice at a time between frames.

06

The server checked 22,808 files four times a second

Found by
A CPU profile of plumber's own server on algorecall: 27 s in one file scan, and 39 full scans in 12 s with nobody connected.
Cause
A safety-net timer under the file watcher re-checks every known file in case an event is missed. It ran every 250 ms on every project. On this one a check costs about 0.2 s, so every answer queued behind a check.
Fix
The net stays, paced by what it costs: a twentieth of the thread with a native watcher, a quarter when polling is all there is. File hashes are kept while a file is unchanged.

07

Every restart starts from nothing: building the warm start

Found by
Profiling a server start, then running the one-off plumber check twice: 43 s, then 6.8 s. The command-line check keeps its result between runs. The server never did.
Plan
The server keeps a table of what it learned plus a receipt of every input. A start may answer from it only after checking it, and only once days of starts show the kept table always equals a fresh one.
Built
Keeping the table, checking it on every start, recording what every import resolved to, a line in plumber doctor, and six tests. Nothing is answered from the table yet.

The check caught something on its first run: on algorecall the receipt was valid but the tables differed. All 2,411 files' readings were identical; the serialiser writes an array densely or sparsely depending on how the engine happens to hold it. The comparison now hashes what the table says, not its bytes.

The rules this left behind

Each one came from a measured number, and they now guide new engine work.

Measure firstThe guess about heavy rules was wrong in order. The timer was right.
Nothing one at a time889 requests, 20 redraws and one file index per question all became batches.
Hot and cold apartSend what is drawn; fetch the rest when someone acts. 811 MB became 12.
Once per distinct inputRe-judge only what a late fact touches; keep a file's index while its text holds.
Tables, not treesEach path and text stored once, numbers in typed columns. 116 MB became 21.
Small slicesNo unit of work bigger than a few milliseconds on the app's main thread.

Mistakes along the way

  • The browser tool silently dropped large answers, so a 46 MB answer first looked like 4.6 MB. Measuring inside the page found it.
  • I twice listed that 46 MB as "not looked into" and offered other work first, until the owner pointed it out.
  • Two freezes of 0.8 s and 2.5 s were first blamed on plumber; they were algorecall mounting itself.
  • The first kept table was 116 MB where I had predicted a few tens.

What is still open

  • A cold start on algorecall still takes about 41 s. The fast start answers from the kept table only after the check has matched through days of ordinary work. It has 12 starts so far.
  • Scrolling with plumber open is 53 frames a second, not 60. About 20 frames in a scroll take double time; their cause is not profiled yet.
  • The receipt is 15.5 MB on algorecall, mostly repeated paths. It needs the same table treatment before the fast start reads it.
  • Judging still runs on the app's main thread. Moving it to a worker is part of the signed-off foundations for new scan modes.
