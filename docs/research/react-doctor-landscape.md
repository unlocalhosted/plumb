# React Doctor and design-system drift tooling

Research snapshot: **9 October 2026**. Primary sources only: official sites/docs, public repositories, npm metadata, and selected implementation files. React Doctor source is pinned in section A; its published rule metadata was compared with npm 0.9.17. Landscape entries are shorter capability assessments. No tools were installed or benchmarked against a real product during this brief; performance and vendor outcome claims remain attributed claims. **UNVERIFIED** means the exact named product or claimed capability could not be established, not that it cannot exist.

Core finding: React Doctor combines project-aware linting, regression comparison, a health score, and grounded agent handoffs. Design-system drift tooling divides into source-policy enforcement, constrained styling APIs, token-graph governance, and design/code context or comparison. Those mechanisms are complementary; none alone establishes visual fidelity. Evidence and exceptions follow.

## A. React Doctor

**Verified 2026-10-09.** Examined live site/docs, source repository at [`281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52`](https://github.com/millionco/react-doctor/commit/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52), npm registry metadata, and published `oxlint-plugin-react-doctor@0.9.17` tarball. Claims below distinguish shipped mechanisms from promotional language. Rule inventory covers published metadata and source, not whichever rules happen to activate in a particular app.

### Product and framing

React Doctor is a deterministic React code auditor with a CLI, lint plugins, programmatic API, agent workflow and PR review integration. Its site frames the problem around unreliable agent-written React; the concrete scope is correctness, performance, security, accessibility and maintainability. It complements existing linting with curated rules and project-level analysis. The current tool also has a separate runtime tracing command; describing the entire product as static-only would be incomplete. [Site](https://www.react.doctor/), [overview](https://www.react.doctor/docs), [runtime command in README](https://github.com/millionco/react-doctor#runtime-performance-traces).

### How it runs

- **CLI:** `npx react-doctor@latest` scans the current project; supply a directory or explicit files to narrow input. npm exposes a `react-doctor` executable. Published 0.9.17 requires Node `^20.19.0 || >=22.13.0`. Core invocation offers `--json`, score-only output, staged scans, explicit time budgets and parallelism controls. [npm metadata](https://registry.npmjs.org/react-doctor/0.9.17), [CLI reference](https://www.react.doctor/docs/reference/cli-reference).
- **CI:** `react-doctor ci install` scaffolds GitHub Actions or GitLab CI. GitHub's `millionco/react-doctor@v2` produces a sticky summary, inline changed-line review comments, logs and optional commit status. Action defaults to advisory (`blocking: none`) and introduced findings; CLI defaults to error blocking. GitLab/other CI can invoke CLI directly. Required branch checks supply actual merge blocking. [CI setup](https://www.react.doctor/docs/ci-and-prs/github-actions-setup), [Action implementation](https://github.com/millionco/react-doctor/blob/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52/action.yml).
- **Editor:** standalone `eslint-plugin-react-doctor` and `oxlint-plugin-react-doctor` bring file rules into existing lint commands and their editor integrations. ESLint presets are `recommended`, `next`, `react-native`, `tanstack-start`, `tanstack-query`, `preact`, plus `all`. Whole-project security scans are metadata-only under these plugins; CLI performs them. No dedicated first-party editor extension was verified. [Plugin docs](https://www.react.doctor/docs/configuration/eslint-and-oxlint-plugins).
- **Agents:** `react-doctor install` installs `/react-doctor` skill for detected agents including Claude Code, Cursor, Codex and OpenCode. Optional non-blocking pre-commit hook scans staged files; optional native Claude/Cursor hooks feed findings back after edits. `--yes` installs skills for detected agents; native hooks additionally require `--agent-hooks`. `--dry-run` previews installation. [Agent installation](https://www.react.doctor/docs/getting-started/install-for-coding-agents).
- **API/MCP:** `react-doctor/api` exposes the programmatic diagnosis/configuration surface. No first-party React Doctor MCP server was verified in package exports, CLI, README or docs. Rules such as `mcp-tool-capability-risk` analyze an application's MCP exposure; their existence does not constitute MCP integration for this tool. [API docs](https://www.react.doctor/docs/reference/node-api), [package exports](https://github.com/millionco/react-doctor/blob/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52/packages/react-doctor/package.json).
- **Runtime:** `react-doctor scan http://localhost:3000` opens system Chrome in a temporary profile, highlights React renders and captures a DevTools performance trace until Enter or five minutes. Text, JSON and JSONL output includes summary and compressed trace path. `--cdp` attaches an isolated authenticated Chrome profile; other open nonblank pages are rejected because tracing is browser-wide. Trace remains local. [Runtime README](https://github.com/millionco/react-doctor#runtime-performance-traces), [runtime CLI definition](https://github.com/millionco/react-doctor/blob/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52/packages/react-doctor/src/cli/index.ts).

### Analysis mechanism

**Static lint:** oxlint hosts React Doctor's JavaScript AST visitors, with `oxc-parser`/OXC supplying parsing infrastructure. The generated configuration explicitly uses `typeAware: false` and turns oxlint's generic built-in categories off. Many React and JSX accessibility rules are ports under `react-doctor/*`; React Compiler diagnostics remain external `react-hooks-js/*`. This is not a TypeScript semantic type checker for the entire application. [Oxlint configuration](https://github.com/millionco/react-doctor/blob/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52/packages/core/src/runners/oxlint/config.ts), [external rules](https://github.com/millionco/react-doctor/blob/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52/packages/oxlint-plugin-react-doctor/src/external-rules.ts).

**Semantic heuristics:** scope/binding analysis and control-flow graphs are built lazily from the AST and memoized per `Program`. Rules can resolve selected cross-file helpers/imports. These make analysis more contextual than string matching, while remaining static approximations. Some project graph utilities use TypeScript's compiler API for local symbol identity, with `noLib`/`noResolve`; that narrow usage does not make normal lint type-aware. [Scope/CFG wrapper](https://github.com/millionco/react-doctor/blob/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52/packages/oxlint-plugin-react-doctor/src/plugin/utils/wrap-with-semantic-context.ts), [cross-file resolver](https://github.com/millionco/react-doctor/blob/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52/packages/oxlint-plugin-react-doctor/src/plugin/utils/resolve-cross-file-export.ts), [limited TypeScript symbol analysis](https://github.com/millionco/react-doctor/blob/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52/packages/core/src/project-analysis/utils/extract-jiti-load-references.ts).

**Whole-project passes:** React component/hook complexity reports cyclomatic/cognitive complexity above 15 and measures nesting. Repeated JSX normalizes data leaves while preserving composition/expression behavior; it reports substantial structural families across the project. [Maintainability measurements](https://www.react.doctor/docs/overview/react-maintainability).

Six optional graph checks cover unused files, exports, types, dependencies, dev dependencies and runtime import cycles. Project parsing uses `oxc-parser`, including extracted Astro/Vue/Svelte/MDX source where supported. Security file scans inspect source/configuration/artifacts. Supply-chain checks query Socket.dev for direct dependency scores; they are enabled by default, including dev dependencies, with threshold 50. Network dependency checking is separate from local AST analysis. [Project parser](https://github.com/millionco/react-doctor/blob/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52/packages/core/src/project-analysis/collect/parse.ts), [graph-rule configuration](https://www.react.doctor/docs/configuration/config-files), [security scan host](https://github.com/millionco/react-doctor/tree/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52/packages/core/src/checks).

### Score, reports and baseline

Health score displays as **0–100**, a server-supplied label, colored bar and doctor face. Local color thresholds are 75 for green and 50 for yellow. No A–F grade scale was verified. **Exact score formula/weights are not public in the inspected repository:** `calculateScore` delegates to `https://www.react.doctor/api/score`, posting gzipped sanitized diagnostics and optional project/run metadata. Response contains score, label and optional per-rule priorities/P0–P3 tiers. Requests remove `fileContext` and `fixGroupId`, sanitize paths and return null on API failure. `--no-score` skips score/share/crash-reporting behavior. This remote scoring request is distinct from anonymous Sentry counters. [Score request code](https://github.com/millionco/react-doctor/blob/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52/packages/core/src/request-score.ts), [score constants](https://github.com/millionco/react-doctor/blob/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52/packages/core/src/constants.ts), [score UI](https://github.com/millionco/react-doctor/blob/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52/packages/react-doctor/src/cli/ink/components/score-header.tsx).

Diagnostics include path, line/column and optional range, plugin/rule, severity, category, human headline, message, fix guidance, docs URL, related locations and optional shared-root-cause `fixGroupId`. JSON schema v3 adds stable identity, normalized paths, tags, projects, score, analyzed-file coverage/completeness, skipped checks, duration and baseline totals. [Diagnostic schema](https://github.com/millionco/react-doctor/blob/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52/packages/core/src/types/diagnostic.ts), [JSON builder](https://github.com/millionco/react-doctor/blob/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52/packages/core/src/build-json-report.ts).

Scopes distinguish **full**, all findings in changed **files**, introduced findings versus base (**changed**), and findings touching changed **lines**. Source also implements `--baseline <report.json>` for a saved JSON report. Comparison reports new/fixed/existing counts and recognizes renames/line shifts; element-level findings can match occurrences to avoid making reformatting a regression. Score remains the head scan's score, not a newly introduced-issues score. If comparison cannot be computed, it reports degraded diff findings and skips the regression gate. Whole-project unused/cycle checks require full scope because partial scopes cannot prove reachability. [Baseline inspection](https://github.com/millionco/react-doctor/blob/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52/packages/react-doctor/src/inspect.ts), [CLI definition](https://github.com/millionco/react-doctor/blob/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52/packages/react-doctor/src/cli/index.ts), [maintainability docs](https://www.react.doctor/docs/overview/react-maintainability).

### AI output and autofix

Agent handoff assembles ranked findings with severity/category, fix recipe, locations and full `diagnostics.json` plus per-rule text files. It asks agents to read files, fix root causes, group shared `fixGroupId` findings as one task, fetch canonical recipes and rerun the real tool. Large migrations get representative-sample and owner-signoff guidance. Per-issue prompts explicitly scope work to one rule and exclude unrelated refactors. Rule documentation is fetchable as Markdown at `/docs/rules/{plugin}/{rule}.md`. [Handoff builder](https://github.com/millionco/react-doctor/blob/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52/packages/react-doctor/src/cli/utils/build-handoff-payload.ts), [single-rule prompt](https://github.com/millionco/react-doctor/blob/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52/packages/react-doctor/src/cli/ink/lib/build-issue-prompt.ts), [rule docs](https://www.react.doctor/docs/rules).

Handoff can copy a prompt to clipboard or launch Claude Code, Codex or Cursor CLI with that prompt. **Implementation detail:** selected agent launches use `--dangerously-skip-permissions`, `--yolo` or `--force`, respectively. This is agent-driven repair, not guaranteed safe mechanical rewriting by a lint fixer. No `react-doctor --fix` CLI or built-in source-code autofixer was verified; its own Rule interface contains visitors/reporting, not fixer edits. Site's autofix wording appears in a user testimonial. Config/setup subcommands do edit configuration/workflow files. [Launcher](https://github.com/millionco/react-doctor/blob/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52/packages/react-doctor/src/cli/utils/launch-agent.ts), [rule interface](https://github.com/millionco/react-doctor/blob/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52/packages/oxlint-plugin-react-doctor/src/plugin/utils/rule.ts).

### Configuration and suppression

`doctor.config.{ts,mts,cts,js,mjs,cjs,json,jsonc}` or `package.json#reactDoctor`; discovery walks upward to repository/monorepo boundary. Closest config wins, CLI overrides it, and multi-project root/child configuration merges keyed rules/categories and unions ignores. Schema autocomplete is available. Rules/categories accept error/warn/off; tags suppress families; compiler-cleanup bucket adjusts selected cleanup checks; `surfaces` independently controls CLI, score, PR comments and CI failure. `ignore.rules` drops results after execution, unlike disabling rules; file ignores and per-file/rule overrides narrow exceptions. Custom oxlint-shaped plugins are opt-in. [Configuration docs](https://www.react.doctor/docs/configuration/config-files), [custom-rule docs](https://www.react.doctor/docs/configuration/add-custom-rules).

Inline `react-doctor-disable-next-line` accepts comma-separated IDs; same-line `react-doctor-disable-line` also works. Foreign ESLint/oxlint disables have their own compatibility handling. `respectInlineDisables: false` audits suppressed findings. `why file:line` explains diagnostic/suppression applicability; `rules list/explain/set/disable/category/ignore-tag` discovers and edits effective policy. Saved baselines provide bulk backlog tolerance without inserting per-site comments. [Suppression implementation](https://github.com/millionco/react-doctor/blob/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52/packages/core/src/evaluate-suppression.ts), [CLI commands](https://github.com/millionco/react-doctor/blob/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52/packages/react-doctor/src/cli/index.ts).

### Frameworks, monorepos, speed and maturity

Auto-detects React/framework/dependency capabilities; documented projects include Next.js, Vite, Astro, TanStack, React Native, Expo and Preact. File/package boundary wrappers keep React Native and Next rules from leaking across mixed workspaces. `--project` accepts workspace package names, paths or `*`; `--yes` selects all detected projects. Monorepo output gives per-project scores and **worst-of aggregate**, avoiding a good app averaging away a bad one. [Framework wrappers](https://github.com/millionco/react-doctor/blob/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52/packages/oxlint-plugin-react-doctor/src/plugin/react-doctor-plugin.ts), [multi-project diagnosis](https://github.com/millionco/react-doctor/blob/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52/packages/api/src/diagnose.ts).

Speed positioning is qualitative; no current audited numeric scan-time or React Doctor-versus-ESLint multiplier was verified. Engine uses Rust-backed OXC/oxlint infrastructure, but custom visitors run as JS. Source shows warm shared worker pools across projects, file/sidecar caches, largest-first balanced batches, lazy shared semantic analysis and capability/import gating. `--no-parallel` and `--no-cache` are available. A benchmark cannot be inferred from the engine brand: project graph scans, custom rules, network score/dependency calls and runtime recording alter cost. Repository's evaluation corpus explicitly excludes 219 slow/incomplete/unfetchable repositories from its default 2,000-project set; that is a corpus limitation, not universal speed proof. [Worker pool](https://github.com/millionco/react-doctor/blob/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52/packages/core/src/runners/oxlint/run-oxlint-job.ts), [lint caches](https://github.com/millionco/react-doctor/tree/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52/packages/core/src/runners/oxlint), [evaluation corpus](https://github.com/millionco/react-doctor/blob/281fdc965635f0c7e3ad7d80d2c98bdf3d92ae52/packages/evals/README.md), [OXC](https://oxc.rs/).

## B. Landscape: enforcement, token governance, and drift

Status: **VERIFIED** means a primary project, package, or vendor document establishes existence and the stated mechanism. Strengths and gaps below are research judgments about that mechanism, not measured rankings. An existing MCP server or sync pipeline does not by itself prove automatic drift detection.

### Tailwind and CSS enforcement

**1. `eslint-plugin-tailwindcss`, including its own v4 rewrite — VERIFIED.** Checks class strings in source through ESLint AST visitors and the Tailwind compiler. The current repository defaults to branch `v4`; its package manifest is 4.4.0. Nine documented rules cover ordering, canonical spelling, negative arbitrary values, shorthands, important-suffix placement, arbitrary-value bans, conflicting classes, unknown classes, and unnecessary arbitrary values. v3 consumers use `@3.x`; v4 requires `cssConfigPath` pointing at the Tailwind CSS entry. **Strength:** compiler-aware validity and autofixes, with explicit arbitrary-value prohibition available. **Gap:** a valid theme utility can still violate component semantics; default recommended settings do not ban every arbitrary value. Calling another project its official v4 successor is inaccurate. [Repository and rule table](https://github.com/francoismassart/eslint-plugin-tailwindcss), [upgrade guide](https://github.com/francoismassart/eslint-plugin-tailwindcss/blob/v4/UPGRADE.md), [manifest](https://github.com/francoismassart/eslint-plugin-tailwindcss/blob/v4/package.json).

**2. `eslint-plugin-better-tailwindcss` — VERIFIED; independent alternative.** ESLint/Oxlint plugin extracts class strings from supported language ASTs and recognized helpers (`cn`, `clsx`, `cva`, `tv`, `twMerge`, etc.), then applies Tailwind-aware rules. Separates stylistic rules from correctness: wrapping/order/canonicalization versus concatenation, unknown/conflicting/restricted classes. Supports v3/v4 with rule-specific differences and per-package `cwd` in monorepos. **Strength:** `no-restricted-classes` accepts regex, custom message, and replacement fix; useful for migrating palette utilities to semantic tokens. **Gap:** house policy must be configured; restrictions need to cover variants/modifiers, and string analysis cannot recover arbitrary runtime construction. [Repository](https://github.com/schoero/eslint-plugin-better-tailwindcss), [restriction rule](https://github.com/schoero/eslint-plugin-better-tailwindcss/blob/main/docs/rules/no-restricted-classes.md).

**3. `@poupe/eslint-plugin-tailwindcss` — VERIFIED; separate v4 CSS plugin.** Registers a Tailwind CSS language using `@eslint/css`, extending CSS parsing for v4 directives and syntax; presets target CSS/PostCSS files. Includes conflicting utilities, arbitrary-value overuse, and theme-token preference. **Strength:** policy for Tailwind's CSS configuration/directive surface, beyond JSX class strings. **Gap:** not the original plugin's successor; its README explicitly separates implemented rules from migration/formatting roadmap items. Do not count planned rules as coverage. [Repository, presets, and roadmap](https://github.com/poupe-ui/eslint-plugin-tailwindcss), [entry-point source](https://github.com/poupe-ui/eslint-plugin-tailwindcss/blob/main/src/index.ts).

**4. `stylelint-declaration-strict-value` — VERIFIED.** Stylelint/PostCSS declaration checks require variables, functions, or allowed values for configured property names/regexes. Supports Sass/Less/CSS variables and exceptions; optional shorthand expansion is experimental and disabled by default. **Strength:** small, configurable hardcoded-value gate across many CSS dialects. **Gap:** allowing a variable does not prove it is a real or semantically suitable design token. Autofix requires a user-supplied `autoFixFunc`; it cannot infer the right semantic replacement. [Project and configuration](https://github.com/AndyOGo/stylelint-declaration-strict-value).

**5. Exact names `stylelint-design-tokens` / `@stylelint/design-tokens` — UNVERIFIED.** Neither exact npm registry endpoint resolved at this snapshot. This is not evidence that token linting is unavailable; several differently named packages below exist. Avoid presenting a generic `@stylelint` token plugin as an official package without its exact identity. [Registry lookup: unscoped](https://registry.npmjs.org/stylelint-design-tokens), [registry lookup: scoped](https://registry.npmjs.org/@stylelint%2fdesign-tokens).

**6. `stylelint-design-tokens-plugin` — VERIFIED, legacy.** Loads a flat token JSON dictionary and maps `env(--token-name)` references to its keys through `designtokens/check`. **Strength:** direct token-name dictionary validation. **Gap:** documented `env()` convention differs from normal modern `var()` usage; flat JSON and npm version 0.0.14 make it a narrow historical example, not a verified general DTCG validator. [Source](https://github.com/LasaleFamine/stylelint-design-tokens-plugin), [npm metadata](https://registry.npmjs.org/stylelint-design-tokens-plugin/latest).

**7. `@kong/stylelint-plugin-design-tokens` — VERIFIED.** `use-proper-token` checks whether a token belongs on the CSS property using it; `token-var-usage` requires the paired CSS-variable/SCSS-fallback form. **Strength:** catches semantic misuse, such as a text token on a background, after basic token adoption. **Gap:** Kong-specific names and fallback convention need adaptation for another system. [Rule documentation](https://github.com/Kong/design-tokens/blob/main/packages/stylelint-plugin-design-tokens/README.md).

**8. `stylelint-plugin-carbon-tokens` — VERIFIED.** Carbon v11+ Stylelint plugin checks CSS custom properties and SCSS variables. Six rules: theme, contextual theme layer, layout, type, motion duration, motion easing. Parses declarations including relevant shorthands/functions; ships recommended, strict, and light-touch presets. **Strength:** motion and contextual layer semantics join basic color/spacing enforcement; some fixes are automatic. **Gap:** Carbon-specific policy and token vocabulary; its production-readiness claim is the project's claim, not a benchmark here. [Repository and rule documentation](https://github.com/carbon-design-system/stylelint-plugin-carbon-tokens), [npm snapshot: 5.0.6](https://registry.npmjs.org/stylelint-plugin-carbon-tokens/latest).

**9. Unknown-token validation: Stylelint core and CSSTools — VERIFIED.** Current Stylelint documents `no-unknown-custom-properties` plus experimental `referenceFiles` for cross-file definitions. The older `stylelint-value-no-unknown-custom-properties` plugin accepts imported token definitions/known names. **Strength:** flags misspelled or deleted tokens using the generated dictionary. **Gap:** known-name validation neither bans raw values nor identifies unused definitions; cross-file loading must reflect real themes. [Stylelint configuration](https://stylelint.io/user-guide/configure/#referencefiles), [customization example](https://github.com/stylelint/stylelint/blob/main/docs/user-guide/customize.md), [CSSTools plugin](https://github.com/csstools/stylelint-value-no-unknown-custom-properties).

### Design-system-specific policy

**10. ### Enforcement through types and compiler-aware rules

**15. Chakra UI `strictTokens` — VERIFIED.** Generated TypeScript style-prop types reject undeclared/raw token values when strict mode is enabled. Custom themes require CLI `typegen` locally and in CI to keep accepted values current. **Strength:** editor feedback before execution, using the actual theme vocabulary. **Gap:** protection is in typed Chakra APIs; raw CSS, untyped JavaScript, casts, and stale generated types remain outside that contract. [Theming and strict mode](https://www.chakra-ui.com/docs/theming/overview), [CLI/typegen requirement](https://www.chakra-ui.com/docs/get-started/cli).

**16. Panda CSS `strictTokens` / `strictPropertyValues` — VERIFIED.** Code generation narrows TypeScript value types. `strictTokens` constrains properties with configured tokens; `strictPropertyValues` narrows enumerated CSS properties. Explicit `[value]` syntax bypasses either constraint. **Strength:** separate token identity from ordinary CSS validity, with a visible escape hatch. **Gap:** strict mode does not mean escape-free enforcement or validate every non-token property; additional policy is needed to review arbitrary values. [Writing styles and exact scope](https://panda-css.com/docs/styling/writing-styles), [configuration defaults](https://panda-css.com/docs/reference/config).

**17. Panda `@pandacss/eslint-plugin` — VERIFIED, current compiler-aware enforcement.** ESLint and Oxlint entry points load the Panda project/compiler, validate token paths/nesting/included files, surface extraction diagnostics, and flag deprecated definitions. Policy includes `prefer-token`, `no-primitive-token`, `prefer-text-style`, logical-property and shorthand consistency. **Strength:** names an existing theme token for a raw-value replacement and can prefer semantic tokens over primitives. **Gap:** many policies are opt-in; recommended token preference covers colors only. Oxlint integration is marked alpha and binds one Panda project per run. [Official lint setup and rule inventory](https://panda-css.com/docs/get-started/linting).

**18. StyleX — VERIFIED; constraints must be designed.** Compile-time style extraction plus static types; `StyleXStyles<{...}>` constrains permitted properties and value unions, `StyleXStylesWithout` blocks properties, and `StaticStyles` excludes dynamic styles. Variable groups/themes provide typed contracts. **Strength:** component authors can define exactly which styling dimensions consumers may override. **Gap:** ordinary StyleX permits literal values; token-only use is not automatic. Official docs acknowledge edge cases where TypeScript accepts extra properties. [Static type constraints and caveat](https://stylexjs.com/docs/learn/static-types/), [API](https://stylexjs.com/docs/api/types/StyleXStyles/).

**19. vanilla-extract + Sprinkles — VERIFIED.** Stylesheets in TypeScript compile to static CSS. Theme contracts give stable typed variable shapes; Sprinkles restricts utility properties/values to the sets defined by the system author. **Strength:** a token-backed finite styling API can make invalid choices unrepresentable for consumers. **Gap:** base `style()` accepts raw CSS values; a theme contract ensures shape/identity, not token-only adoption everywhere. [Project](https://vanilla-extract.style/), [theme contract](https://vanilla-extract.style/documentation/api/create-theme-contract/), [Sprinkles](https://vanilla-extract.style/documentation/packages/sprinkles/).
